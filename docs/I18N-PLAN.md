# Kirari 多语言实施计划

> 目标：**真正能多语言阅读** —— 不只是界面文案切换，文章正文、页面内容、评论都要能读。
>
> 已定方案：中文（默认，根路径）+ 英文（`/en/` 前缀）；评论自建渲染并加小字译文。

---

## 一、已定决策

| 项 | 决定 | 理由 |
| --- | --- | --- |
| 语种 | 中文 + 英文 | 界面已有 10 套翻译，但文章要逐篇翻；两种语言可控 |
| URL | 中文在根、英文 `/en/` 前缀 | 现有链接、SEO 权重、已分享出去的地址全部不受影响 |
| 评论 | 自建渲染 + 小字译文 | giscus 是跨域 iframe，父页面无法注入翻译 |

---

## 二、当前状态与障碍

`i18n()` 定义在 `src/i18n/translation.ts`，实现是：

```ts
export function i18n(key: I18nKey): string {
  const lang = siteConfig.lang || "en";   // ← 构建期全局读取，与页面无关
  return getTranslation(lang)[key];
}
```

**核心障碍**：语言是全局常量，不随页面变化。全站 **31 处调用、分布在 17 个文件**，其中相当一部分结果被用作 `aria-label`、`title` 等属性或组件 props，不是纯文本节点 —— 所以「客户端替换文本」这条路走不通，必须让语言成为**渲染期的参数**。

---

## 三、分阶段实施

### 阶段 1 · i18n 基础设施（无可见变化）

- `astro.config.mjs` 加 i18n 配置：
  ```js
  i18n: {
    defaultLocale: "zh_CN",
    locales: ["zh_CN", "en"],
    routing: { prefixDefaultLocale: false },
  }
  ```
- 新增 `src/i18n/utils.ts`：
  - `getLangFromUrl(url)` —— 从路径前缀解析当前语言
  - `useTranslations(lang)` —— 返回绑定该语言的 `t(key)` 函数
- 保留旧的 `i18n()` 作为兼容层（内部走默认语言），**逐个文件迁移**，避免一次性改 31 处引入回归。

**验收**：`astro check` 与构建通过，站点外观零变化。

### 阶段 2 · 页面路由

Astro 的 i18n 路由不会凭空生成页面，文件结构仍需存在。为避免把每个页面写两遍：

1. 把每个页面的主体抽成组件（如 `src/components/pages/ArchivePage.astro`）
2. `src/pages/archive.astro` 与 `src/pages/en/archive.astro` 都只是薄壳，各自传入 `lang`

涉及页面：首页（含分页）、归档、关于、友链、展板、标签页、分类页、404。

**验收**：`/archive/` 与 `/en/archive/` 均可访问且文案正确；`sitemap` 收录两套；每页带 `hreflang` 互指。

### 阶段 3 · 文章内容翻译

- 目录结构：`src/content/posts/en/<slug>.md` 存英文版，中文版保持原位
- `content.config.ts` 从路径推导 locale，`getSortedPosts(lang)` 按语言过滤
- **译文由 AI 在写作期生成并提交为静态文件**，与文章简述同一策略 —— 文章数量不多，不值得接第三方翻译 API，也不必每次访问都实时翻
- 缺译文时：`/en/posts/x/` 回落到中文原文，顶部加一条「这篇还没有英文版」的提示，而不是 404

**验收**：至少一篇文章有完整英文版并可通过 `/en/posts/<slug>/` 访问；缺译文的回落提示正确。

### 阶段 4 · 语言切换器

- 导航栏加入切换控件，在当前路径上增删 `/en` 前缀并跳转
- 记住选择（localStorage），但**不做自动跳转** —— 强行按浏览器语言重定向会让人找不回原文
- 文章页若无对应语言版本，切换器指向该语言的首页而非死链

**验收**：任意页面切换后停在对应语言的同一页面。

### 阶段 5 · 评论自建渲染 + 小字译文（**依赖 token**）

现状 giscus 是 iframe，跨域，父页面既读不到也改不了里面的内容。

- 用 GitHub Discussions GraphQL API 取回本页讨论的评论列表，自己渲染
- 每条评论下方以小字显示译文
- **发表评论仍然交给 giscus** —— 自建发表需要处理 OAuth 与写权限，风险和维护成本都高

> ⚠️ **阻塞项**：GitHub Discussions API 即便对公开仓库也强制要求鉴权。
> 需要在仓库 Settings → Secrets and variables → Actions 配置一个只读 token
> （`public_repo` 权限足够），构建期取数。

**验收**：文章页显示评论列表与小字译文；未配置 token 时自动退回纯 giscus，不报错。

## 四、译文从哪来

| 内容 | 来源 |
| --- | --- |
| 界面文案 | 仓库已有 10 套 locale 文件，直接用 |
| 文章正文 | AI 生成，提交为静态 md 文件 |
| 文章标题/简述/描述 | 同上，写在译文的 frontmatter 里 |
| 评论 | 构建期取回后翻译，缓存为静态 JSON |

---

## 五、风险与取舍

- **维护成本翻倍**：以后每写一篇文章都要跟一份英文版。缺译文有回落机制，不会挂掉，但双语完整度靠自觉。
- **构建时间与产物体积增加**：页面数接近翻倍。
- **繁体中文未纳入**：可用脚本做简繁转换，但「软件/軟體」这类术语差异需要人工校对，先不做。
- **不做自动语言跳转**：按 `Accept-Language` 强制重定向会让中文读者打不开被分享的英文链接，反之亦然。
